*"Show me a bone and I will reconstruct the beast." Georges Cuvier said it about a femur. `native/organs/what.js` says it about a 3.2 MB Vite bundle, and means it exactly as literally.*

## The instrument that chokes, named precisely

The EO Reader's ordinary path is a recursive prose reader: split the material into encounters, find candidates, let a fold accumulate significance. That path is correct for prose and was measured to fail on code — not as a hunch, as a logged number. `adapters/code/encounters.js`'s own header states the specimen: `textEncounters`'s sentence splitter found **174 "sentences" in a real 3.2 MB bundle, the largest one 1.8 MB** (`native/adapters/code/encounters.js:6-8`). A minified bundler emits a handful of physical lines carrying hundreds of kilobytes each; asking a sentence-grained perceiver to hold one as an "encounter" is asking it to swallow a book in one bite. The fix disclosed in the same file is not a smarter prose reader — it is the admission that code is a *different grain* and needs its own segmentation, one encounter per physical line, hard-capped at 16,000 characters (`CODE_MAX_ENCOUNTER_CHARS`, `encounters.js:32`) and cut at real statement boundaries (`,` `;` `}` `)` `]` `>`, and a backtick) before falling back to whitespace, before falling back to a hard cut (`encounters.js:81-105`).

Before any of that segmentation runs, something has to decide the material *is* code at all, and that gate is itself measured rather than asserted. `isCodeHunk` fires on three structural signals — very long lines (average over 400 characters; the real specimen measured **2,588 lines across 3.2 MB, ≈1,236 characters per line**, `encounters.js:38-39`), bundler fingerprints (`__vite__`, `webpackJsonp`, `require(`), and brace/semicolon density — plus a fourth, added after a disclosed false negative: a 65 KB real Flask application, whose short unminified lines and total absence of braces failed all three code signals and read as *not code* until a Python-declaration ratio test (three or more `def`/`class`/`import` lines, at least twice as many call-parens, and one colon-terminated declaration header) was added specifically to close that gap (`encounters.js:47-54`). The same comment discloses the test that keeps the new rule honest in the other direction: prose *about* code — "class struggle shapes history" — clears the line-shape and paren-ratio bars but never ends a line with a declaration colon, so it is still refused. This is the wiki's own standard for a heuristic: state the case it got wrong, state the fix, state the adversarial case that still has to fail.

## The five things read off the bytes, not asserted about the app

Once the material is admitted as a code hunk (or, since a later addition, a GraphQL introspection document), `native/organs/what.js` — Handle: **Cuvier**, after the paleontologist who reconstructed the whole animal from the bone in hand — composes an account from exactly five sources the artifact's own bytes state, never more:

> *the MODULE MAP — every module/asset name the bundle's own bytes state; the VENDOR STACK — the libraries and bundlers the bytes name; the FEATURE MODULES — the map's non-vendor modules, the app's own parts; the ENDPOINTS/STRINGS — the paths and names the literals declare; the DECLARATIONS — whatever the source syntax names* (`what.js:14-18`)

Each has a real extraction behind it, in `adapters/code/scan.js`. The module map is built from hashed Vite-style filenames, `assets/` paths, and quoted `import`/`from` statements, classified `vendor` when the bare name carries a known package word (`VENDOR_WORD`, a regex over ~30 received ecosystem names — react, antd, lodash, d3, and so on, `scan.js:41`), `asset` when it ends in a static extension, and `feature` otherwise. The classifier keeps a fourth bucket the naive vendor/feature split would erase: `infra` — a chunk named `ui-vendor-…` or `utils-vendor-…`, carrying the bundler's own "-vendor-" naming convention but no known package word in the leading position. `scan.js`'s own comment states why this bucket exists rather than folding into either neighbor: *"asserting it as a third-party vendor (or as one of the app's feature modules) would both be wrong"* (`scan.js:89-94`). That is the organ refusing to launder an ambiguous byte into a confident category — the same discipline [The Two Doors](/the-two-doors) enforces at the evidence layer, applied here to naming.

Vendor identity itself is disclosed as a *received-name heuristic*, never a verdict: `VENDOR_FINGERPRINTS` is a list of literal byte patterns (`__vite__`, `from "react"`, `@apollo/client`) that name only libraries and bundlers, explicitly never an application product (`scan.js:43-46`), and `composeVendors` merges a fingerprint hit with a vendor-classed module-map row for the *same* library into one identity rather than double-counting — "repetition inside one signal is never sold as independent corroboration," in the words of the chorus-log entry that reviewed this exact merge (`CHORUS-LOG.md`, 2026-09-16 S128 entry, Pearl row). Declarations — the fifth source — are not read by `what.js` at all; they are read by `adapters/text/code-structure.js::codeGist`, injected rather than re-derived, and filtered against **CodeNamePrior@1, a baseline of 26 real files across 16 distinct security-audited/landmark repos in C, Go, Python, and TypeScript** (`code-structure.js:29-30`): a name this material declares that also recurs across ≥2 of those independent codebases (`genericFloor = 2`, `code-structure.js:369`) is dropped as boilerplate before the account ever sees it — `main`, `init`, `run` do not make the cut; `LicenseStatus` does.

## Gated, not top-N — ranked by measured occurrence, cut on a disclosed window

The organ's second discipline is about how a list gets shortened, and it is stated as a rule before it is implemented as code: *"every list is cut by a declared window with its full count disclosed, ordered by measured occurrence in the material… never by insertion order"* (`what.js:30-32`). The mechanism for feature-module names is `occurrencesOf` — a literal word-boundary count of how many times a module's bare stem appears in the scanned window (`what.js:53-60`) — which `composeAccount` uses to sort `featureRows` before slicing to `DEFAULT_MAX_FEATURE_NAMES = 24` (`what.js:47,70-74`). The account line that results says explicitly how many were left out: `"${featureNames.join(", ")} (${featureTotal - featureNames.length} more)"` (`what.js:93`) — a disclosed remainder, not a silent truncation. Endpoint literals get the same treatment through a different scorer: `distinctiveStringsFrom` scores every non-generic string literal by whether it looks like an API path, a slash-delimited route, or a component name, keeps a witness count per distinct string, and caps the list at `maxKeep` while reporting `literalsScanned` and `scored` totals in its own `basis` string (`scan.js:352-379`). Declared names go through a third gate again, `resolutions.js`'s own `dmdCut` — the same measured-not-declared-budget ladder [Kleene Up](/kleene-up-physics-of-finding) documents for Lens/Paradigm reads elsewhere in the reader — reused, not re-derived, per `what.js`'s own header (`what.js:19-20`).

The scan window itself is bounded the same way: `maxScanChars` defaults to 400,000 characters (`what.js:196`), and when the material exceeds it, `scanHunk` reports `scannedChars`, `skippedChars`, and `sampled: true` rather than reading the rest silently (`what.js:224-225,238-245`; `scan.js:394-405`). A regression test pins this directly: handed a hunk with 300,000 trailing filler characters and `maxScanChars: 8_000`, the organ reports exactly `skippedChars: giant.length - 8_000` and a disclosure string matching `/skipped/` (`what.test.mjs:75-82`).

## The same reconstruction, a different skeleton

Since a change logged as S129 in the repository's chorus log, `whatIsThis` routes a GraphQL introspection document (`{"__schema": {"types": […]}}`) to a second composer, `composeSchemaAccount`, before the code-hunk gate ever runs (`what.js:201-220`). The routing test is structural, not a guess: `isGraphqlSchema` requires the document to parse as JSON and carry a non-empty `__schema.types` array where every entry has both a `name` and a `kind` (`adapters/code/graphql.js:28-35`) — JSON that merely happens to contain the string "graphql" is not enough, and the test suite pins the negative case directly (`{"a": 1}` still returns the ordinary `not_code_hunk` refusal, `what.test.mjs:134-137`).

What the schema account states is, again, only what the introspection document's own bytes carry: total type counts by kind, the root Query/Mutation/Subscription types and their field counts, and — flagged explicitly as convention, not fact — the `*Connection` pagination shape, the `*Payload` mutation-return shape, a domain-vocabulary tally over the first CamelCase word of every object type name, and a mutation-verb tally over an 89-verb received list (`create`, `update`, `submit`, `resolve`, and so on, `adapters/code/graphql.js:55`). Every one of these carries the same disclosed-heuristic pattern in its evidence basis — a *"received … convention, disclosed"* clause, naming the GraphQL, PascalCase, or plain convention in turn, appears four separate times across `composeSchemaAccount`'s evidence rows (`what.js:145,150,166,172`) — because a schema that names a type `LicensePayload` is *stating* a convention, not proving the mutation actually returns a license. Byte anchors for the root-type claims resolve to a real `"name"` string offset in the raw document (`graphql.js:137-138`), so even the schema path keeps the discipline that a claim without an offset is not admitted as evidence.

## What the account refuses to say, and how it says so

Three typed refusals sit ahead of every composition path: empty material, material that scans as neither code nor a GraphQL schema, and a caller that failed to inject `dmdCut` (`what.js:41-45`). That last one is worth pausing on, because it is a refusal about the *caller*, not the material — `whatIsThis` will not silently re-derive the measurement organ codeGist already requires; a missing dependency is a typed gap (`what:dmd_cut_injected`), never a fallback default (`what.js:197`). And when a hunk's scanned window yields nothing at all — no module map, no vendor fingerprint, no banner, no declaration — the organ does not stay silent either; it emits a `sparse` line stating exactly that: *"the scanned bytes yield no module map, no vendor fingerprints, no banners, and no declarations — the hunk is code-shaped but carries no identifying structure in its scanned window"* (`what.js:113`). A negative finding is composed with the same evidence discipline as a positive one — the same posture [The Guardrail Organs](/the-guardrail-organs-witnesses-not-verdicts) documents for the reader's other typed-refusal surfaces.

## Cuvier's own paperwork, read against itself

The organ's law is that an account is *"never a verdict"* (`what.js:24`) and that *"it does not name a product the bytes do not state, and it says so when asked to"* (`what.js:26-27`). Held to that standard, the organ's own status in this pass has to be disclosed rather than assumed, and two things surfaced under exactly that check.

First, running the organ's own test file directly (`node --test native/organs/what.test.mjs`) returns **10 of 11 tests passing**. The one failure is `capacities: the \`what\` row is registered, domain-legal, and resolves to this organ` (`what.test.mjs:28-37`), which asserts `findCapacity("what")` resolves to `{ fn: "whatIsThis", op: "DEF", terrain: "Lens" }`. `native/organs/capacities.js` — the registry `findCapacity` reads, an exact-id lookup by design, with fuzzy matching explicitly named future work rather than attempted (`capacities.js:515-521`) — carries no row with `id: "what"` anywhere in its 537 lines, confirmed by a direct search of the file. The organ works; its own capacity-seam registration, which its own test suite expects, is not currently present in the registry it is meant to resolve against. That is a disclosed gap, not a working claim — the organ passes its behavioral tests and fails its own wiring test.

Second, `README.md`'s Handle table cites `what.js`'s work as "READING-SPEC S128/S129" (`README.md:391`). `native/READING-SPEC.md` does carry entries numbered S128 and S129, but both were **renumbered at a 2026-09-25 consolidation merge** from earlier numbers (S116→S128, S113→S129, `READING-SPEC.md:6113,6133`), and the content now sitting at those numbers is unrelated — a standing check for NL-facing organs' language-scope hygiene, and the partial retirement of the legacy-eoreader6.1 submodule. The Cuvier/code-hunk and GraphQL-schema work is logged, in full, under those same labels — S128, S129 — in `CHORUS-LOG.md`'s entries of 2026-09-16, written *before* the consolidation renumbered `READING-SPEC.md`'s own sequence out from under them. A repo-wide search for "Cuvier," "code hunk," or "GraphQL schema artifact" inside `READING-SPEC.md` itself returns nothing. The citation in the README's own Handle row therefore points, as of this pass, to the wrong entries in the current spec file — a small, mechanical instance of the same failure mode [Holons](/holons) already logged one layer up, at organ ownership rather than operator naming: two records that once agreed have drifted apart, and "a miss in one registry is not a miss in both."

Neither finding says the organ is broken. `whatIsThis` runs, refuses typed, discloses its sampling, and composes an account from real bytes on both a bundle and a schema — the 10 passing tests demonstrate exactly that. What both findings say is narrower and, by this wiki's own standard, more useful: the account an organ gives of *itself*, in a README table or a spec citation, is not exempt from the same bar the organ holds the material to. A number that used to resolve can stop resolving the moment something upstream of it — a renumbering, a registry that was never wired — moves. Cuvier's own discipline, applied reflexively: this too is an account, not a verdict, and it says so.
