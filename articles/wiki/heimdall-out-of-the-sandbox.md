*A watcher that runs inside the thing it watches is not a watcher. It is a passenger.*

## The wedge

On the night of 2026-09-19, `proxy.mjs` — the process that fronts eoreader7's local model on port 11436 — went into an infinite microtask self-loop: 98.5% CPU for roughly ten hours, unreachable on `/health` and `/heimdall`, deaf to SIGTERM (`native/docs/HEIMDALL-FLEET.md:6-14`). A `sample` trace and the logs pinned the cause to a runaway promise loop hot in `String.prototype.split`, with an ESTABLISHED TCP connection from the proxy back to its own port.

The detail that makes this an EO problem rather than a Node problem is where the watcher was standing when the floor gave out. `heimdall.mjs`, the in-process supervisor, ran *inside* `proxy.mjs`. `proxy.mjs:2891-2904` narrates the lesson in its own inline comment, written the day after: "a proxy that wedges into a CPU self-loop (10h at 98.5%) takes an in-process watcher down with it — nobody outside could see it." The watcher did not fail to notice the wedge. The watcher *was* wedged, along with everything else in that process's event loop. There was no one outside to see it, and no one outside to ask.

## One Handle, two eras

The name survives the redesign; the address does not, and the difference between those two facts is the whole article. `heimdall.mjs`'s own header spells out the Handle in full: "the god who stands at Bifröst and watches. He sees and hears everything, keeps watch against the day the bridge fails, and sounds the horn when danger comes" (`heimdall.mjs:1-8`). That module still exists, still runs *inside* `proxy.mjs` by default, still drives a `DEF → EVA → REC` loop over the local surfaces, and still answers on the admission gate every request passes through (`README.md:94`, "the same Heimdall admission gate"). It is not deprecated; `ER7_EXTERNAL_HEIMDALL=1` is opt-in, not a replacement.

What changed after 2026-09-19 is that a *second* thing now carries the name, in a different process, on a different port, with a narrower job: `native/heimdall/*.mjs`, entered via `heimdall-fleet.mjs` (port 11438 by default). The old Heimdall watches the proxy's surfaces from inside; the new fleet watches the proxy — and its own peers — from outside. `proxy.mjs:2912-2918` is the literal fork in the code: when `ER7_EXTERNAL_HEIMDALL` is unset, `startWatcher({ selfPort: PORT })` runs in-process exactly as before; when it is set to `1`, the proxy skips `startWatcher` entirely, logs "EXTERNAL heimdall — proxy is a sandbox," and answers only its own honest `/heimdall` for the fleet to probe. The Handle names a doctrine (watch, warn, never act alone) that both modules follow; the sandbox boundary is the actual engineering claim, and it is what the rest of this article is about. Treat the Norse coloring as exactly that — coloring. It explains why the module is easy to find in a grep and easy to talk about in a standup; it explains nothing about whether the design holds.

## The three layers, out of process

`native/heimdall/fleet.mjs` describes itself — and, in substance, the modules it composes — as deliberately dependency-light: it "never imports the proxy, never runs a model, and never holds a socket it does not own" (`native/heimdall/fleet.mjs:17-23`). Three modules, three questions.

**Self — `native/heimdall/self-health.mjs`.** Two mechanical signals, neither model-involved (lines 11-17): an event-loop heartbeat, a `setInterval` that fires every `LAG_TICK_MS` (default 1000ms, line 29) and measures how late it actually runs; and a self-CPU read off `ps -p <pid> -o %cpu=` (line 110), paced by `CPU_SAMPLE_MS` (3000ms, line 34) so it never runs on the hot path. `selfStanding()` (lines 122-142) derives `healthy | lagging | wedged` from a *sliding window* of the last `WINDOW_MAX = 16` samples (line 63) — `lateCount >= WEDGE_SAMPLES` (5, line 33) means wedged; `worstLagMs > LAG_WORST_MS` (250ms, line 32) means lagging. The module states its falsifying control as a literal field on every standing read — `falsifyingControl: "a late heartbeat followed by an answered probe concedes wedged"` (line 140) — the same rule `HEIMDALL-FLEET.md:49-50` states in prose.

**Peers — `native/heimdall/peer-mesh.mjs`.** A pure state machine, no sockets, no kills (lines 19-22). A peer is any process answering `/heimdall`. `isCandidate()` (lines 93-114) marks a peer a candidate when it is down or self-reports wedged, *or* when it keeps answering while the box is externally saturated — the second clause did not exist before 2026-09-20, and the next section explains why it had to be added. `escalate()` (lines 130-148) raises a candidate with a human-readable `ask` — `"should we terminate <peer>? (<reason>)"` — and a `status: "pending"`. `decide()` (lines 150-160) applies an operator's answer, and only an explicit `allow: true` sets `applied: true`; an explicit no is recorded as `denied`, and silence past `ESCALATION_TTL_MS` (180 seconds, line 23) instead lapses the ask via `expirePending()`. `recordProbe()` (lines 65-91) is where a peer answering a probe concedes any open escalation outright (lines 73-80) — reachability is evidence *against* termination, never neutral.

**Fleet — `native/heimdall/fleet.mjs` + `heimdall-fleet.mjs`.** The tick loop: sample self, read box load, probe every peer, raise every candidate, expire stale asks (`fleet.mjs:165-197`). `WELL_KNOWN` (lines 37-40) seeds the mesh with the proxy's address; `configuredPeers()` (lines 50-62) extends it from `ER7_HEIMDALL_PEERS`, falling back to a peers file on disk (`readPeersFile`, lines 65-72) so a managed restart does not lose the mesh. `status()` (lines 199-217) discloses `lastTickAt` (line 167, set at the top of every tick) alongside every peer's standing — the field that matters most in the next section.

The three layers correspond, loosely but exactly, to a `DEF → EVA → REC` pass run on the fleet itself rather than the proxy: `self-health.mjs`'s own header calls itself "a REC holon: it DEFines health, EVA-luates the sample, and REC-ords a standing... with its falsifying control." Whether that is REC in the strict operator sense or a looser family resemblance to it is worth being precise about, and the honest answer is closer to family resemblance: what actually earns the label in this codebase is the discipline, not the operator wiring — see [Holons](/holons)'s account of REC as "transforming the conditions for transformation" rather than the state itself, which self-health does not attempt on its own standing (only an external peer can).

## Never terminate silently

The rule that survives every rewrite, stated four ways in `HEIMDALL-FLEET.md:114-120`: never terminate silently, never convict on absence alone, a watcher that cannot watch itself cannot watch anything, and the watcher runs out of the sandbox. The mechanical version of "never silently" is `peer-mesh.mjs`'s `escalate`/`decide` pair: nothing in the mesh — no timer, no probe result, no self-standing read — ever calls anything that stops a process. The furthest the code reaches on its own is `peer-mesh.mjs`'s `escalate()` setting `peer.candidate = true`, followed by `fleet.mjs`'s `raiseToOperator()` printing a line to stderr (or POSTing to `ER7_HEIMDALL_OPERATOR_URL`, `fleet.mjs:97-114`). Applying a termination requires a human or a configured operator channel to answer `POST /decide {"id": "...", "allow": true}` (`README.md`/`HEIMDALL-FLEET.md:96`).

This is the same shape of doctrine [The Two Doors](/the-two-doors) names at the reading layer: a prior "may condition orientation, nominate perceptions, and focus interrogation. They cannot become witness merely by being prior." `witness.js`'s Thymus doctrine is "nomination is not admission." Heimdall's escalation is the operations-layer cousin of the same rule: a candidate is nominated by a probe or a self-report, but it is not admitted to termination merely by being nominated. The `/decide` endpoint is the admission gate; everything upstream of it only proposes.

The `--operator matrix` channel is named in the docs, which describe a `heimdallRoomBody` function in `the-fold/matrix.js` as the intended peer channel — a public-join fleet directory room for heimdall WebRTC signaling. But no `the-fold/matrix.js` file exists anywhere in the current tree, and `heimdallRoomBody` appears nowhere as actual code — only as this forward-looking description, repeated near-verbatim in `peer-mesh.mjs`'s own header comment and in `HEIMDALL-FLEET.md`. As of this writing it is not just a reserved seam, it is an undrafted one: `--operator log` and `--operator http` are the two channels that actually run (`HEIMDALL-FLEET.md:76-80`). Worth saying plainly rather than letting the diagram imply otherwise.

## The falsifying control that would break the whole design — and it did, twice

`HEIMDALL-FLEET.md:122-129` states the design's own kill condition before anyone ran it: a fleet process that itself wedges and no other fleet or operator notices concedes the entire self-watch claim. On 2026-09-20 the control was actually run, not just written down, and it broke the design in two distinct places.

**Falsification 1: self-health cannot see its own hard wedge.** A wedged event loop starves the very heartbeat that is supposed to measure it — the `setInterval` callback never fires, `lateCount` stays at 0, and `selfStanding()` reads `healthy` on a process pegged at 98.5% CPU. `native/heimdall/falsify-self-health.test.mjs:18-27` pins this as a *passing* test titled `"FALSIFY: a loop whose heartbeat cannot fire reads healthy (false negative)"` — the assertion is that the false negative happens, not that it doesn't. The comment at the top of the file is unambiguous about what this means: "self-health cannot detect a hard wedge from inside, because the measurement runs on the wedged loop... The design survives ONLY because an EXTERNAL peer/operator watches the fleet." This is not framed as a bug fixed away — `native/docs/HEIMDALL-FLEET.md:138` calls it "an honest boundary" — and the fix is disclosure, not detection: `fleet.mjs` exposes `lastTickAt` on every `status()` read (`fleet.mjs:167,199-217`) so a peer or operator can see a fleet that has stopped ticking, even though the fleet itself cannot. `falsify-fixed.test.mjs:73-78` pins that the field is populated after a tick; the earlier limitation is left standing, not patched over, because it cannot be patched from inside — a fleet has no way to sample a thread that has stopped scheduling anything, including its own sampler.

**Falsification 2: an answering-but-spinning peer is invisible.** The incident proxy answered its own `/health` and would presumably have answered `/heimdall` too — it was reachable, just also spinning a core at 98.5% for ten hours. `peer-mesh.mjs`'s original `isCandidate()` had no path from "answers 200" to "candidate." The fix adds a second, independent signal that no single peer can hide by wedging: `fleet.mjs:124-137`'s `readBoxLoad()` shells out to `sysctl -n vm.loadavg` on every tick and calls the box "saturated" above a floor (`ER7_HEIMDALL_LOAD_FLOOR`, default 8). `recordLoad()` (`peer-mesh.mjs:116-128`) accumulates `saturatedTicks` on every peer that is currently answering; `isCandidate()`'s second clause (`peer-mesh.mjs:110`) fires once that count reaches `SATURATED_SUSPECT_TICKS` (default 3, `peer-mesh.mjs:27`), and the resulting escalation reads "should we terminate er7? (answers but the box has been saturated N ticks, external load M)" (`fleet.mjs:187-189`). The falsifying control on the fix has its own test: saturation that clears resets the counter to zero rather than convicting on a single spike (`falsify-fixed.test.mjs:41-51`, `peer-mesh.mjs:125`). `falsify-fixed.test.mjs:80-95` runs the whole path end to end — three saturated ticks against a peer that answers every one of them, and the fleet raises it anyway.

One caveat the source itself does not flag, worth stating because the wiki's standard is to disclose limits as readily as wins: `sysctl -n vm.loadavg` is the BSD/macOS spelling of load average, not the Linux one. `readBoxLoad()`'s own catch block (`fleet.mjs:134-136`) swallows any failure — a missing binary, a wrong platform, a timeout — into `{ load1: null, saturated: false }`. There is no `os.platform()` check and no log line on that path. On a host where the command errors, Falsification 2's fix silently reopens: an answering-but-spinning peer goes back to being invisible, and nothing in the running system says so. This is a real gap in the fix's portability, not a claim made anywhere in the docs; it follows directly from reading `fleet.mjs:127-137`.

## Two more fixes, found by running the live fleet rather than a unit test

`HEIMDALL-FLEET.md:163-196` records a second pass, dated the same day, where the *live* fleet (not a test harness) violated two more of its own standing rules.

**A recovered process read `wedged` forever.** The original `self-health.mjs` tracked `lateCount` and `worstLagMs` as monotonic accumulators — an all-time worst that never came back down. A process whose event loop stalled once during the incident's aftermath kept reporting `standing: "wedged"` for days afterward, with `worstLagMs` in the millions, even after its most recent lag had dropped to 1ms. That is a direct violation of the module's own stated control — "a busy-but-answering process must never read wedged" — by construction: the standing was answering a different question (*has this process ever been bad?*) than the one it claimed to answer (*is this process bad now?*). The fix, now load-bearing in the current code, is the sliding-window design already described above: `lagSamples` holds only the last `WINDOW_MAX = 16` samples, `selfStanding()` derives `worstLagMs`/`lateCount` from that window alone, and the all-time value survives only as `peakLagMs`, explicitly disclosure-only and never read by the standing logic (`self-health.mjs:46-54,116-142`). `self-health.test.mjs:49-61` pins the recovery case directly, with a fixture worst lag of 8,577,894ms (roughly two hours twenty minutes) and a clean recent window: the assertion is `standing === "healthy"` while `peakLagMs` still discloses the old number as history. (That 8,577,894ms figure is the test's fixture value, not an independently measured figure from the actual incident — it stands in for "a very bad episode," and the test does not claim otherwise.) `self-health.test.mjs:63-69` checks the converse: a window that is *still* late correctly stays wedged, so the fix is a real window, not a blanket reset.

**Fleets could not watch each other.** `WELL_KNOWN` was hardcoded to the proxy's own two addresses (`fleet.mjs:37-40`), so a second `heimdall-fleet.mjs` process had nowhere to register as a peer of the first — the hive-mind's stated premise, "no single watcher is unreachable," was unwired for the case of two fleets. `ER7_HEIMDALL_PEERS` (`fleet.mjs:50-62`, `configuredPeers()`) and its on-disk fallback (`readPeersFile`, lines 65-72, read from a file written beside the pid so a managed restart does not drop the mesh) let N fleets configure each other as peers, so a fleet that stops ticking or self-reports wedged gets raised by a *sibling* fleet, not only by the proxy it watches. `fleet.test.mjs:93-147` pins three cases under the `MULTI-HEIMDALL:` prefix: one fleet learns to probe a second via the env var; a silent peer fleet gets raised exactly like any other peer (`"should we terminate fleet3"`); and the persisted peers file survives when the env var itself is absent, which is the actual restart-safety property, not just the coordination one.

## What the numbers actually say

`HEIMDALL-FLEET.md:101-104` reports "19 tests" across the `heimdall/*.test.mjs` suite. Counting the `test(` calls in the current tree (`native/heimdall/*.test.mjs`, run via `npm run test:heimdall`) gives 34: 8 in `self-health.test.mjs`, 7 in `peer-mesh.test.mjs`, 9 in `fleet.test.mjs`, 7 in `falsify-fixed.test.mjs`, 3 in `falsify-self-health.test.mjs`. The gap is not cause for alarm — the doc predates the recovery/coordination pass and the falsify-self-health file that pins Falsification 1 directly — but it is a stated number that no longer matches the file it describes, and the wiki's own standard is to say so rather than repeat a stale figure as current.

The operational benchmark that is supposed to catch regressions in this area, `native/eval/heimdall/benchmark.mjs` (`npm run benchmark:heimdall`), scores six axes on a 0-100 scale, one of which (axis 5, `FLEET`) checks specifically for "no stale wedged standing (a recovered process reads healthy)" and another (axis 6, `COORDINATION`) checks that "the fleet mesh contains every expected peer heimdall" when `ER7_BENCH_PEERS` is set (`benchmark.mjs:13-18`) — the axis-6 header comment itself names the variable `ER7_BENCH_FLEET_PEERS`, but the code that actually reads it, at line 32, uses `ER7_BENCH_PEERS`; that mismatch is in the source, not introduced here, and `ER7_BENCH_PEERS` is the name that works. Both axes are direct regression checks on the two live-fleet fixes above; whether the benchmark has actually been run against a live multi-fleet deployment as opposed to the unit-test peers is not something this article can verify from the source alone, and it is left as an open question rather than an assumed yes.

## Whose job this doesn't do

Heimdall's fleet decides whether a *process* is alive, responsive, and not quietly cooking the box; it has no opinion on whether that process's *answers* are any good. That is deliberate scope, not an oversight, and it lines up with the distinction [The Guardrail Organs](/the-guardrail-organs-witnesses-not-verdicts) draws between witnessing and adjudicating: an escalation is Heimdall proposing a fact about a process's reachability and the box's load, never a verdict about what the process said. The remedy vocabulary Heimdall's own doctrine lends to content-level self-healing — pace/defer/downgrade/escalate/re-forge/quarantine — is exercised by a different organ pair, Apollo and Thea (`README.md:372`), which "crafts the remedy from Apollo's finding plus the swarm's report, in Heimdall's own vocabulary... proposes, never executes." Same non-execution discipline, same borrowed words, different failure surface: see [Apollo & Thea: the Self-Healing Loop](/apollo-thea-self-healing-loop) for what that pair does with a bad *answer* rather than a dead *process*.
